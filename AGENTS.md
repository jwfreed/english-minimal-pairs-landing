# Soundwise Landing Site

Repository contract for coding agents.

## Scope and architecture

This is the public acquisition and SEO site for the Soundwise iOS app at
`https://getsoundwise.co`.

- Vite 7 multi-page build, vanilla JavaScript modules, static HTML, and CSS.
- GitHub Pages hosting with a custom `CNAME`.
- No backend, database, API, or server-side code.
- The simple architecture is intentional. Do not add a framework, CMS, router,
  or build layer for routine page work; see `docs/site-structure.md`.

The app repository, `jwfreed/english-minimal-pairs`, owns learner experience,
contrast training logic, and app capabilities. This repository owns public
acquisition, SEO/localized marketing pages, and the App Store conversion path.
It represents app capabilities; it does not define them.

Optimize for qualified learner intent:

- explain learner problems accurately;
- represent app capabilities truthfully;
- connect search intent to available practice.

Do not broaden pages into unrelated generic English-learning content.

## Production invariants

- `vite.config.js` is authoritative for what ships and consumes the shared SEO
  route registry. A page reaches production only when its source path appears
  in `build.rollupOptions.input` directly, through `SEO_PAGE_SLUGS` in
  `src/seo-page-routes.js`, or through `legalLocales`. Development mode and
  direct file browsing can serve an unregistered page that production omits.
- `content/locales/<locale>/index.html` is generated by
  `npm run generate:localized-homepages` from `index.html` and supplemental
  translations. Never hand-edit these localized homepage files.
- Every indexable page is self-canonical. A localized cluster must use one
  identical reciprocal `hreflang` set. `public/sitemap.xml` may contain only
  built, intentionally indexed pages.
- Existing validation scripts are release gates derived from production
  failures. Fix failures; never route around them.

## Capability and learning claims

When capability is unclear, inspect app documentation and implementation and
use conservative wording. Never invent app features, exercises, learning
methods, analytics, or scientific claims.

`CONTRAST_CATALOG` in `src/contrast-catalog.js` is authoritative for real
listening exercises on this site. A page may promise an exercise only when its
contrast ID is cataloged and `src/seo-page.js` mounts the exercise. Otherwise,
describe the contrast or link to an existing supported contrast.

The learning objective is the sound contrast; a word pair is an example.
Prefer “Practice the /ɪ/ vs /iː/ contrast using examples like ship/sheep and
bit/beat” over “Master ship/sheep.” Use a `[Word A] vs [Word B]` title or H1
only when that exact pair exists in the catalog. Broader phonemic coverage does
not authorize an exact-pair exercise claim.

## Localization

Localized pages are variants of the English source, not independent products.

- Transcreate naturally while preserving teaching sequence, SEO intent, and
  claim boundaries.
- Keep English target words visible when search intent depends on them.
- Preserve section IDs and TOC anchors unless a change is necessary.
- Link only to existing production-ready practice pages.
- Apply `docs/messaging-framework.md` by meaning, not literal wording.
- Never introduce accent-fixing, native-like, clinical-proof, guaranteed
  improvement, or equivalent claims in any language.

## Development and change strategy

Use Node.js `20.19+` or `22.12+` and npm.

```bash
npm ci
npm run dev
npm run build
npm run preview
```

There is no configured linter, formatter, or type checker.

For SEO metadata, localization, routing, generated content, deployment, or
analytics changes:

1. Find the closest existing implementation and source of truth.
2. Understand generation, build, and validation consequences.
3. Make the smallest change that follows the established pattern.

Do not add one-off abstractions, dependencies, large rewrites, or unrelated
refactors without explicit instruction.

For marketing copy, preserve meaning and claim scope. Do not add urgency,
guarantees, unsupported outcomes, or generic copy at the expense of the
learner problem and next action.

## Analytics

Analytics changes are production changes. Inspect existing events, preserve
event names, prevent duplicates, and verify parameters before adding
dimensions. Measure only website behavior available to this repository. An App
Store CTA click is measurable; an in-app practice completion is not. Do not
create proxies that imply unavailable data.

## Tool routing

- Use direct reads for isolated HTML, copy, or metadata changes.
- Use CodeGraph for shared SEO, localization, exercise, route-registration,
  validation, or build flows spanning files.
- For visible changes, run the site and use Playwright to inspect the rendered
  page and interaction.

## Verification

Before completing a code or content change, run:

```bash
npm test
npm run build
```

Run relevant additional gates:

```bash
npm run validate:landing-copy
npm run validate:funnel-tracking
npm run validate:app-store-tracking
npm run validate:seo-conversion-matrix
npm run validate:localized
```

For visible changes, inspect the rendered page in a browser.

## Deployment

`.github/workflows/deploy.yml` deploys GitHub Pages:

```text
push to main
→ npm ci
→ npm run build
→ write getsoundwise.co to dist/CNAME
→ deploy GitHub Pages
```

There is no staging environment. Do not push to `main` or trigger deployment
without explicit approval. See `docs/deployment.md`.
